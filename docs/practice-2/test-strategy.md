## 1. Цель тестирования
   - Все сервисы в статусе health
   - Процессинговая цепочка успешно проходит от начала до конца при валидных значениях карты и суммы транзакции
   - Для каждой причины отказа система даёт результат, соответствующий техническому заданию
   - Система отклоняет транзакцию в случае поведения, которое считается некорректным

## 2. Объекты тестирования:
   - СМП:
     - авторизация
     - управление картами
     - маршрутизация
     - симулятор терминала
     - симулятор мерчанта
     - логгер
     - сервис отправки уведомлений
     - сервис-точка входа для API-запрсов
     - bin-lookup сервис

## 3. Уровни тестирования:
   - модульное: проверка бизнес-правил внутри каждого сервиса изолировано
   - функциональные проверки API: проверка api-контрактов между сервисами
   - интеграционное: роверка взаимодействия с бд, rabbitMQ
   - E2E: прохождение полной цепочки транзакции

## 4. Область тестирования:
   - что войдёт:
     - проверка бизнес логики: самая важная область для корректной работы системы
     - проверка связности системы: важно, чтобы система корректно обрабатывала ситуации, когда каклй-либо из сервисов недоступен
   - что не войдёт:
     - нагрузочное тестирование: излишне для системы **медленных** платежей
     - безопасность: на данный момент не входит в область приоритетов
     - тестирование dashboard: на данный момент не входит в область приоритетов

## 5. Подход к организации:
   - Риск-ориентированный + аналитический подход: согласно с ISTQB CTFL
   - Принципы приоретизации определяются риском, а не удобством или объёмом кода для достижения максимальной эффективности тестирования

## 6. Итог:
   - Authorization и Card Management получают максимальную глубину проверок, так как ошибка здесь напрямую ведёт к неверному поведению транзакции или неверному расчёту баланса. Bin Lookup, Gateway, Switch, симуляторы, Logger, Notification Service получают только чек-лист дымового тестирования и критического пути.
