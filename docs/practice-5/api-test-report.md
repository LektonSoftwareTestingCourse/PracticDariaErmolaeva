## 3. Валидация

| Поле или параметр | Правило | Классы | Границы и проверенные значения | Кол-во проверок |
|---|---|---|---|---:|
| `bin` при создании карты | BIN задан в допустимом формате | Допустимый, слишком короткий | `400000`, `12` | 2 |
| `pan` в пути получения карты | 16 цифр | Допустимый формат, слишком короткое значение | Созданный PAN, отсутствующий 16-значный PAN, `123` | 3 |
| `limit`, `offset`, `bin` при получении списка карт | Положительный `limit`, неотрицательный `offset`, корректный BIN | Валидный запрос, по одному невалидному параметру | `limit=1`, `limit=0`, `offset=-1`, `bin=123` | 4 |
| `count` при генерации карт | Минимум одна карта | Минимальное допустимое и значение ниже границы | `1`, `0` | 2 |
| `mti`, `pan`, `currencyCode`, `mcc` публичной авторизации | `mti=0100`, PAN из 16 цифр, код валюты из 3 символов, MCC из 4 цифр | По одному неверному полю в запросе | `1234`, `123`, `RU`, `54111` соответственно | 4 |
| `pan` для внутреннего логирования | 16 цифр | Слишком короткий PAN | `123`, проверяются `400`, имя поля и сервис-источник | 1 |
| `limit` и `offset` поиска | `1 ≤ limit ≤ 500`, `offset ≥ 0` | Допустимая пагинация, значения за пределами диапазона | `limit=1` с `offset=0` и `1`, ошибки при `limit=0`, `501` и `offset=-1` | 4 |
| `status` поиска | Значение из перечисления | Допустимые значения, неизвестное значение | `APPROVED`, `DECLINED`, `UNKNOWN` | 3 |
| `dateFrom` и `dateTo` | Допустимая дата, начало не позже конца | Корректный диапазон, неверный формат каждой границы, обратный диапазон | Даты текущей транзакции, `invalid`, `2026-11-02 > 2026-11-01` | 4 |
| `granularity` графиков | Допускаются `hour` и `day` | Недопустимое значение | `week` | 1 |

## 5. Обоснование достаточности

Набор проверяет основные HTTP-контракты по созданию карты, авторизации, записи транзакции и её поиску. Для подготовки данных используются HTTP-вызовы и отдельные PAN, STAN или UUID. JSON тела формирует `TestDataFactory`, а карту через API создаёт `TestCardFactory`. Для публичных запросов и прямых вызовов Authorization и Logger задана общая спецификация REST-assured.

Тестами не покрыты `GET /health` как служебная проверка доступности, прямые обращения к BIN Lookup, как обращения к внешнему сервису, и отдельные проверки уведомлений, потому что они относятся к асинхронной части обработки транзакции.
